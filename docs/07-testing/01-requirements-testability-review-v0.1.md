# 需求可測性審查：短網址服務（G1 前置）

> 目的：確認每條 REQ／NFR 驗收標準是否具備客觀可觀察判準。  
> 判定用語：**可測**＝現有驗收即可設計 TC／檢查表；**有條件可測**＝驗收有客觀判準，但依賴尚未產出之設計／SEC／環境基線；**不可測**＝驗收本身無客觀判準（須企劃修法）。  
> 本輪 **無不可測** 條目；有條件項以開放問題追蹤，不因此整條判不可測。

## 2. 功能需求（REQ）可測確認

| 編號 | 摘要 | 可測？ | 測法類型 | 問題／備註 |
|---|---|---|---|---|
| REQ-001 | 合法長網址建立短碼並回傳可造訪短網址 | 可測 | API／整合（建立→以短碼回查） | Given／When／Then 完整；可對 SC-01 |
| REQ-002 | 有效短網址 HTTP 重新導向至長網址 | 可測 | API／HTTP（狀態碼、`Location`） | 「約定方法」建議於 OpenAPI 寫死（預設 GET）；見 G1-QA-O1 |
| REQ-003 | 成功導向時點擊次數原子＋1；失敗不計 | 可測 | API／整合（導向前後查次數；失敗路徑對照） | 可對 SC-05、SC-08；並發一致性可併競態抽樣 |
| REQ-004 | 查詢指定短碼目前點擊次數 | 可測 | API | 回傳非負整數且與成功導向次數一致；可對 SC-09 |
| REQ-005 | 長網址驗證（非空、可解析、僅 http／https、長度≤上限） | 可測 | API／否定路徑 | 長度邊界執行時依賴文件化 L（見 REQ-011）；驗證規則本身可測 |
| REQ-006 | 短碼符合文件化字元集與長度規則 | 有條件可測 | API／否定路徑 | 規則「可機器驗證」已要求；**具體字元集／長度待 ADR**。ADR 產出前可起草 TC 骨架。見 G1-QA-O2 |
| REQ-007 | 建立驗證失敗回傳明確錯誤且不落庫 | 可測 | API／資料查核 | 例：`invalid_url`；建議錯誤類型清單於設計／OpenAPI 定案（G1-QA-O3，非阻擋可測） |
| REQ-008 | 短碼不存在回傳明確錯誤；不導向、不計次 | 可測 | API／HTTP | 例：`not_found`；可對 SC-06、SC-10 |
| REQ-009 | 對外錯誤不洩漏堆疊／路徑／SQL／原始例外 | 可測 | 負向檢視回應本文 | 可對各錯誤路徑抽樣；細節可與 SEC 對齊 |
| REQ-010 | 已建立短碼全域唯一（含並發） | 可測 | API／競態 | 多次建立比對短碼集合；並發建立不產生重複 |
| REQ-011 | 長網址最大長度 L 文件化且行為一致 | 有條件可測 | API 邊界＋文件審查 | 驗收以「文件化 L」為準：L 可建、L+1 不可建。**L 待設計寫入 OpenAPI**。見 G1-QA-O4。**不判不可測** |
| REQ-012 | 同一長網址可多次建立為不同短碼 | 可測 | API | 優先級「可以」；兩次成功且短碼可不同、皆導向同一長網址 |
