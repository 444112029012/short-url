## 2. 維運部請安全部評估的三點

### 2.1 規則行為變動（R1）
逐一看過上游 patch：
- **resolve（#1792）**：`TryResolve` 加了一個判斷，只要型別檢查器已知道某個運算式是**編譯期常數**，就視為已解析。這只會讓常數不再被報。常數不可能帶入外部輸入，所以 G202、G204 等注入規則對變數的判定不受影響；上游測試仍保留「typed variable 轉 string 要報」的案例。**收窄合理，不構成漏報風險。**
- **G303（#1784）、G102（#1787）**：都是多解析常數。G303 現在能辨識常數路徑，G102 現在能辨識 `":" + port` 這類字串串接。兩者都是**擴大**偵測，原本漏報的情況現在會被報。
- **G112（#1781、#1797、#1798）**：一方面承認「先建立 http.Server、之後才指定 timeout」的寫法，以及透過 struct field 指定的寫法，屬於收窄；另一方面新增「timeout 明確設為 0 或負值也要報」，屬於擴大。收窄部分只在**確實指定了非零 timeout** 時才不報，合理。
- **G118（#1782）**：cancel 經 channel 交出後視為已處理，屬於收窄。這條是 context 洩漏規則，本專案的阻擋門檻是 `-severity=high`，影響很小。
- **G125（新增）、G706 擴充、G602 兩項**：屬於擴大偵測或修正誤判。
- **其他**：#1779 改成用絕對路徑載入檔案，修正巢狀模組的情況，V4、V5 兩版都掃到 57 個檔案，掃描範圍沒有縮小。#1786 調整 concurrency 預設值，不影響結果。autofix 相關的 commit 只影響 AI 修補功能，本專案 CI 沒有啟用（沒有設定金鑰）。
- **結論：可接受。** 這些收窄都限於編譯期常數或已確認有效的設定，沒有收窄到能讓外部輸入漏報的地方。不需要新增金絲雀樣本，沿用 G404 金絲雀即可（K4）。

### 2.2 「新增三個間接依賴」
- 這個說法**與證據不符**。coder/websocket v1.8.15、pb33f/go-yaml v0.1.1、otel/log v1.47.0 早在 CR-002（707f227）就已帶入（13 號檔 §3），v2.30.0 沒有新增依賴（證據 15，48 對 48）。
- CR §6 R5 的寫法「兩版皆含、非本 CR 新增」才是正確的。請在 v0.2 統一措辭（K5）。
- 依賴升版的部分只影響 gosec 工具本身，CI 沒有啟用 AI autofix，風險低。

### 2.3 GO-2026-6809（R2）
- 這是 gosec 二進位用 Go 1.27.2 建置時帶入的標準庫漏洞（crypto/x509 `Certificate.Verify`），新舊兩版都有，**不是本 CR 新增的**。
- gosec 在 CI 裡只做本機靜態分析，autofix 沒啟用時不會發出 TLS 連線，所以在這個用法下沒有可利用的路徑。
- 專案本身的 `govulncheck ./...` 在 symbol 層是 0（轉述，CI 的 sca-govulncheck 也一直是綠的）。
- **同意依 C8 另開 CR 升 Go 1.27.3**（一次只改一件事），但要有期限：建議**在 CR-005 合併後 14 日內提出**，最遲 2026-11-20（K6）。
- 在那之前，此項登錄到 05 號檔，記為 RR-010 的後繼項，評等「低」。
